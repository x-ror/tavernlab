# memreader — читання пам'яті власного клієнта Hearthstone

Спайк, написаний за рішенням від 2026-08-31 (докладніше — `docs/DESIGN.md`,
розділ «Правовий режим»): живий трекер (Арена-драфт, а тепер і будь-який
бій — Ranked/Casual теж) читає стан гри напряму з пам'яті вже запущеного
клієнта замість парсингу `Power.log`/`Zone.log` із затримкою.

**Тільки читання.** Жодного запису в чужу пам'ять, жодного виконання коду
в цільовому процесі, жодної мережі. Технічно — той самий клас прийому, що
й у HDT/Firestone (HearthMirror), але сам HearthMirror приватний і його
код тут не використовується; це написано з нуля на основі відкритого коду
самого Mono-рантайму та загальнодоступного опису техніки.

## Чому це окремий крейт, а не частина `cli`

Компілюється й запускається під звичайним Linux-тулчейном (не Windows-крос-
компіляція) — процес Hearthstone тут працює під Wine, тобто це вже
нативний x86-64 Linux-процес, і `process_vm_readv` читає його пам'ять без
жодної Windows-прошарки. Тому інструмент простий: `cargo run -p memreader`.

Zero-dependency правило (CLAUDE.md) дотримано: `process_vm_readv`
викликається прямим `extern "C"` оголошенням символу glibc (в ній з 2012
року), без крейта `libc`.

## Статус: підтверджено живими даними (2026-08-31)

`--probe` — механічна частина (PID → модуль → PE-експорти →
`mono_get_root_domain` → `MonoDomain*`) — стабільно працює.

`--deep` іде набагато далі й підтверджено на реальних активних іграх
(перевірено проти справжнього `Power.log` того самого сеансу):

- `MonoDomain → domain_assemblies → Assembly-CSharp → MonoImage →
  class_cache` — повний список ~16 000 класів, включно з `Entity`,
  `Player`, `DraftManager`, `PowerProcessor`.
- Для `Entity`/`Player` знайдено `MonoVTable*`, а через нього — усі живі
  екземпляри просто скануванням купи на літеральний патерн вказівника
  vtable (без подвійного розіменування на кандидата, це і швидко, і надійно).
- **`Entity` — 64 (`0x40`) байти, підтверджено**: `+0x30` = `cardId`
  (`System.String`, UTF-16 — свій декодер `try_mono_string`, оскільки
  Mono-рядки не `char*`), `+0x38` = `EntityID`. Перевірено впритул:
  ентіті, чий `cardId` розшифрувався як `HERO_09dbp` (Lesser Heal), мав
  `+0x38 == 57` — точно те `id=57`, яке того ж моменту показував
  `Power.log` для того самого героя.
- **`Player` — `+0x120`** = ім'я (`battleTag`, `System.String`), **`+0x164`**
  = `playerId`. Підтверджено на 20+ живих об'єктах із різних минулих ігор:
  `xror` завжди `playerId=1`, кожен суперник — завжди `2`, без винятків.
- **`Entity` теги — `List<Tag>` на `+0x10`**: не Dictionary. Кожен `Tag`
  має `Name` (`GAME_TAG`) на `+0x10` і `Value` на `+0x14`. Жива вибірка:
  `JAIL_912` → `ENTITY_ID=52`, `CONTROLLER=2`, `ZONE=1` (PLAY), як у
  `Power.log` того ж бою; `HERO_09dbp` → `id=57`, `controller=2`, `ZONE=PLAY`.
  `ZONE`/`CONTROLLER`/`ZONE_POSITION`/`ATK`/`HEALTH`/`COST` читаються з
  цього списку. Три інші поля (`+0x18` `List<Tag>`, `+0x20`/`+0x28`
  `List<TagList>`) на тих самих об'єктах були порожні.

Кожен крок або спрацьовує чисто, або друкує **конкретну** причину і що
з цим робити — жодних мовчазних `unwrap()`. Усі офсети — з підписом рівня
впевненості в `src/mono_layout.rs`.

## `--snapshot`: машиночитаний вивід для інтеграції

```
cargo run -p memreader -- --snapshot
```

Той самий обхід, що й `--deep`, але **весь діагностичний друк іде в
stderr**, а в stdout — рівно один JSON-документ:

```json
{"game":{"turn":4,"step":6,"currentPlayer":1,"idCap":81},
 "entities":[{"addr":"0x74a91480","cardId":"HERO_11","id":64,...}],
 "players":[{"addr":"...","name":"xror","playerId":1,"entityId":2}, ...],
 "sides":[{"playerId":1,"name":"xror","current":true,"mana":3,"manaMax":4,
           "armor":0,"hero":{...},"play":[...],"hand":[...],"deck":20,"graveyard":2},
          {"playerId":2,...}]}
```

`entities` — лише поточна гра: GameEntity разом із Player id=2/3 в одному
острові купи, дедуп по `EntityID` (спочатку повніший об'єкт, потім ближчий
до GameEntity). Герой — тег `HERO_ENTITY` (27) на Player. `--board` друкує
той самий зріз у stderr.

Кожен `entity`/`player` несе ще й `rawTags` — **повний** список
`(GameTag, значення)` з його `List<Tag>`, не лише ту жменьку, що
розкладена по кураторських полях (`zone`/`atk`/...). Це для того, щоб
наступного разу досліджувати живу гру можна було просто запитом до
`/api/memory`, без термінала й повторного запуску `memreader` вручну —
саме так і варто шукати офсети `TAG_DAMAGE`, ключових слів (`Taunt`,
`Divine Shield`, ...) чи причину бага з `sides` нижче.

Це те, що `tavernsim watch` (чи будь-який інший споживач) може безпечно
запустити як підпроцес і розпарсити `tavernlab_json::Json::parse` —
жодного людського тексту в stdout не потрапляє. `cardId`/`name`/будь-який
тег бувають `null`, якщо `MonoString*` не вдалося розшифрувати, або тег
відсутній у `List<Tag>` цього конкретного об'єкта (наприклад, карта в
колоді ще не має `ZONE_POSITION`).

**Вирішений баг (від 2026-09-01, закрито 2026-09-02 — див. нижче):
`sides` іноді плутав, хто є хто.** Живою перевіркою
під час реальної гри виявлено, що `build_sides` міг прив'язати геть чужі,
застарілі `Player`-об'єкти (з давно завершених матчів) замість справжніх
поточних — рука одного гравця показувалась як рука іншого, герої
переплутані. Причина глибша, ніж просто "найближчий адресою": реальна
поточна пара `Player`-об'єктів БУЛА знайдена скануванням (правильні
імена, стоять поряд у пам'яті), але поле `entity_id` в них читалось як
явно неправдоподібне число (мільярд+), тоді як у хибної пари воно було
негативним сміттям — жодне з двох не було надійною ознакою "це насправді
той самий матч". Якір `game_entity()` (по `id==1`) теж не завжди
приземлявся в тому самому острові пам'яті, що й правильна пара гравців.

**2026-09-02: дві реальні причини усунуто.** (1) `build_sides` більше не
падає назад на "найближчий Player за адресою взагалі" — коли в межах
`SAME_GAME_WINDOW` немає жодного `Player` з потрібним `player_id`, ім'я
сторони лишається `null`, а не позичається з чужого матчу; дошка
(`hero`/`play`/`hand`/...) все одно наповнюється незалежно від цього
імені, бо йде з `CONTROLLER`/`ZONE`-тегів. (2) `PlayerHit.entity_id`
тепер завжди `None` замість того неправдоподібного числа — офсет `+0x38`
підтверджений на `Entity`, не на `Player`, а власний `List<Tag>` `Player`
за припущеним офсетом читається порожнім, тож нічого надійного видавати
не було. (3) `game_entity()` більше не вибирає якір лише за кількістю
сусідніх `id 2/3` чи наявністю `TURN`/`STEP` — тепер рахує топологію
дошки (герой у `PLAY` для кожного контролера, не більш як 7 істот) як
головний, лексикографічний критерій, який теги/сусіди не можуть
переважити (перша спроба цього фіксу сама наступила на ті самі граблі —
плаский бонус за `TURN`/`STEP` міг переважити топологію застарілого
острова над живим без тегів; знайдено й виправлено адверсаріальним
рев'ю до коміту). Знімок тепер несе чесний `"confidence": "high"/"low"/
"none"` — сигнал, чи знайдено героя для обох сторін, а не гарантія.

**Досі відкрито (потребує живого клієнта):** `entity_id` через тег 53
(`Player`'s власний `List<Tag>`-офсет не підтверджений живо), і
справжній корінь — прив'язка до синглтона замість евристик над купою
взагалі. **Перша спроба 2026-09-02 проти реальної гри дала конкретний,
а не вигаданий, негативний результат:** класу `GameState` (як і
`GameMgr`/`GameLogic`/`ZoneMgr`) під точно такою назвою в
`class_cache` цієї збірки просто немає (перевірено напряму через новий
`MEMREADER_DUMP_CLASSES=<шлях>` на `--deep` — весь список ~16 000
класів, а не лише фільтр за ключовими словами) — публічні назви з
HearthMirror-подібних джерел застаріли за ці роки. `find_singletons`
тепер цілить і ширший список (`GameEntity`, `SceneMgr`, `InputManager`,
`TurnStartManager`), і в `Player` реально знайшлось одне стабільне
статичне поле (не шум) — але воно вказує НЕ на живого `Player` цього
матчу (звірено з `--snapshot` того ж моменту), тож відкинуто. Також
**Виправлення власної помилки:** спершу здалось, що `find_vtable`
недетермінований (`PowerProcessor` не знайшовся в першому запуску,
знайшовся в наступних) — але це просто клас, ще не зачеплений рушієм
на той момент матчу; повторний прогін пізніше в тому самому матчі —
стабільно 3/3. Офсети `MONO_CLASS_RUNTIME_INFO`/`_DOMAIN_VTABLES`
звірено проти реального коду Mono (github.com/mono/mono) — правильні.

**Баг зі сторонами закрито по-справжньому (2026-09-02).** `GameState`
таки існує — причина, чому цей файл його не бачив, була в тому, що
`MonoImage.class_cache` — хеш-таблиця, де колізії йдуть ланцюжком через
поле в самому класі (`MonoClass.next_class_cache`), а стара
`dump_class_names` читала лише перший клас у кожному "кошику" й тихо
губила решту, включно з `GameState`. Виправлено (офсет
`MONO_CLASS_NEXT_CLASS_CACHE=0x108`, підтверджено живо).

Далі — `find_self_typed_static` теж дивився не туди: слот, який код уже
обчислював, тримає не самі статичні дані, а **вказівник** на окремий
блок (`MonoVTable.has_static_fields`, підтверджено проти реального коду
Mono). Виправивши це, `GameState.s_instance` знайшовся одразу, а в
ньому — `m_playerMap`, прямий, авторитетний список гравців поточного
матчу. **`build_sides` тепер бере гравців звідти в першу чергу** (без
жодного вікна пам'яті чи евристики) — старий евристичний шлях (PR1/PR2)
лишається лише запасним варіантом, коли `GameState` не резолвиться (не
в матчі, стара збірка). Живо звірено проти `Power.log` — збігається
точно, стабільно на кількох послідовних опитуваннях.

`/api/memory` тепер несе `"source": "game_state" | "heuristic"` —
чесний сигнал, яким шляхом відповідь отримана.

**Новий інструментарій (2026-09-02):** `--find-all-singletons` —
сканує self-typed static не лише в TARGETS, а в усіх класах з
резолвнутим vtable (~6с на ~16000 класів). `--dump-addr 0x<адреса>` —
сирий дамп полів довільної адреси (для перевірки кандидата, знайденого
іншим способом). `MEMREADER_DUMP_CLASSES=<шлях>` на `--deep` — весь
список назв класів у файл. Одна реальна, ще не підтверджена зачіпка:
`PowerSpellController` дав один стабільний екземпляр (не шум), але ні
його прямі поля, ні один рівень вказівників углиб не ведуть на
`Entity`/`Player`/`GameEntity` (перевірено програмно). Детальніше й
наступні кроки — `docs/research-report.txt`, розділ A.7 PR3.

**Звужено офлайн-тестами (2026-09-01):** синтетичний тест
(`build_sides_prefers_a_player_in_the_same_heap_island_over_a_closer_stale_one`,
`main.rs`'s `#[cfg(test)]`) підтверджує, що `build_sides`'s
`SAME_GAME_WINDOW`-фільтр сам собою працює правильно — коли якір
(`game_entity()`) вказує в правильний острів пам'яті, застарілий
`Player` поза вікном відкидається на користь живого. Це звужує підозру
до самого `game_entity()`: у тому реальному дампі жоден кандидат
`id==1` (і застарілий, і той, що виявився правильним островом) не мав
`TURN`/`STEP` тегів узагалі — можливо, справжній живий `GameEntity`
просто не потрапив у список кандидатів `id==1` (ліміт сканування?), а
не що він потрапив, але його відкинули. Наступний крок — саме тут, зі
свіжим `rawTags`-дампом під рукою (див. вище) вже не через термінал.

## Як запускати разом зі мною

1. Переконайтесь, що Hearthstone запущений (бажано — активна гра, не
   головне меню, щоб було з чим звіряти).
2. `cargo run -p memreader -- --deep` і скиньте мені весь вивід.
3. Найкорисніше — секція «4 невідомі вказівники» після таблиці Entity:
   там мають бути `Tag name=49 (ZONE)` / `50 (CONTROLLER)` / `53
   (ENTITY_ID)` для живих карт. Звірте з `Power.log` того ж моменту.

## Права доступу

`process_vm_readv` вимагає того самого користувача (не root, не sudo) і
дозволеного `ptrace_scope`:

```
cat /proc/sys/kernel/yama/ptrace_scope
```

`0` або `1` мають працювати для процесу, запущеного тим самим користувачем.
`2` чи `3` — заблокують читання; тоді знадобиться або тимчасово знизити
`ptrace_scope` (`sudo sysctl kernel.yama.ptrace_scope=0`), або дати
`CAP_SYS_PTRACE` бінарнику.
