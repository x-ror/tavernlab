# memreader — читання пам'яті власного клієнта Hearthstone

Спайк, написаний за рішенням від 2026-08-31 (докладніше — `docs/DESIGN.md`,
розділ «Правовий режим»): живий трекер (Арена-драфт, а тепер і будь-який
бій — Ranked/Casual теж) читає стан гри напряму з пам'яті вже запущеного
клієнта замість парсингу `Power.log`/`Zone.log` із затримкою.

**Тільки читання.** Жодного запису в чужу пам'ять, жодного виконання коду
в цільовому процесі, жодної мережі. Технічно — той самий клас прийому, що
й у HDT/Firestone (HearthMirror), але сам HearthMirror приватний і його
код тут не використовується; це написано з нуля на основі відкритого коду
самого Mono-рантайму та загальнодоступного опису техніки.

## Чому це окремий крейт, а не частина `cli`

Компілюється й запускається під звичайним Linux-тулчейном (не Windows-крос-
компіляція) — процес Hearthstone тут працює під Wine, тобто це вже
нативний x86-64 Linux-процес, і `process_vm_readv` читає його пам'ять без
жодної Windows-прошарки. Тому інструмент простий: `cargo run -p memreader`.

Zero-dependency правило (CLAUDE.md) дотримано: `process_vm_readv`
викликається прямим `extern "C"` оголошенням символу glibc (в ній з 2012
року), без крейта `libc`.

## Статус: підтверджено живими даними (2026-08-31)

`--probe` — механічна частина (PID → модуль → PE-експорти →
`mono_get_root_domain` → `MonoDomain*`) — стабільно працює.

`--deep` іде набагато далі й підтверджено на реальних активних іграх
(перевірено проти справжнього `Power.log` того самого сеансу):

- `MonoDomain → domain_assemblies → Assembly-CSharp → MonoImage →
  class_cache` — повний список ~16 000 класів, включно з `Entity`,
  `Player`, `DraftManager`, `PowerProcessor`.
- Для `Entity`/`Player` знайдено `MonoVTable*`, а через нього — усі живі
  екземпляри просто скануванням купи на літеральний патерн вказівника
  vtable (без подвійного розіменування на кандидата, це і швидко, і надійно).
- **`Entity` — 64 (`0x40`) байти, підтверджено**: `+0x30` = `cardId`
  (`System.String`, UTF-16 — свій декодер `try_mono_string`, оскільки
  Mono-рядки не `char*`), `+0x38` = `EntityID`. Перевірено впритул:
  ентіті, чий `cardId` розшифрувався як `HERO_09dbp` (Lesser Heal), мав
  `+0x38 == 57` — точно те `id=57`, яке того ж моменту показував
  `Power.log` для того самого героя.
- **`Player` — `+0x120`** = ім'я (`battleTag`, `System.String`), **`+0x164`**
  = `playerId`. Підтверджено на 20+ живих об'єктах із різних минулих ігор:
  `xror` завжди `playerId=1`, кожен суперник — завжди `2`, без винятків.
- **Не підтверджено:** `Zone`/`Controller` (чиє поле/рука конкретного
  ентіті). Спроба знайти їх серед 4 інших полів `Entity` (`+0x10/+0x18/
  +0x20/+0x28`) показала, що це вказівники на щось на кшталт зв'язних
  списків (кожен веде на структуру, що сама починається з правдоподібного
  вказівника), а не прямий `Dictionary<GameTag,int>` — тож ці офсети поки
  не використовуються. `cards()`/`play()`/`hand()` за конкретним гравцем
  наразі неможливі без цього; є лише "яка карта", "чий id", "чиє ім'я".

Кожен крок або спрацьовує чисто, або друкує **конкретну** причину і що
з цим робити — жодних мовчазних `unwrap()`. Усі офсети — з підписом рівня
впевненості в `src/mono_layout.rs`.

## Як запускати разом зі мною

1. Переконайтесь, що Hearthstone запущений (бажано — активна гра, не
   головне меню, щоб було з чим звіряти).
2. `cargo run -p memreader -- --deep` і скиньте мені весь вивід.
3. Найкорисніше зараз — секції «таблиця Entity» та «таблиця Player» в
   кінці виводу: перевірте, чи `cardId`/`id`/ім'я/`playerId` там
   збігаються з тим, що показує `Power.log` цього самого моменту.

## Права доступу

`process_vm_readv` вимагає того самого користувача (не root, не sudo) і
дозволеного `ptrace_scope`:

```
cat /proc/sys/kernel/yama/ptrace_scope
```

`0` або `1` мають працювати для процесу, запущеного тим самим користувачем.
`2` чи `3` — заблокують читання; тоді знадобиться або тимчасово знизити
`ptrace_scope` (`sudo sysctl kernel.yama.ptrace_scope=0`), або дати
`CAP_SYS_PTRACE` бінарнику.
