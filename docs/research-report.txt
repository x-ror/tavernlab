  **BREAKTHROUGH, 2026-09-02, later the same session.** The web
  research (below) turned up two independent, actively-maintained
  (commits within the last month) public projects both still using
  `GameState`/`s_instance` against the current build:
  `BattlegroundsHelp/bgtracker` (`native/msync`, a clean-room rewrite,
  commits 2026-08-11/12) and `Zero-to-Heroes/unity-spy-.net4.5`
  (Firestone's own tracker library, commit 2026-08-22). Both resolve
  `GameState` via a proper class-table lookup scoped to the
  `Assembly-CSharp` image, not a heap scan -- which is exactly what
  this file's own `dump_class_names` already does (walks
  `MonoImage.class_cache` on the resolved `Assembly-CSharp` image).
  So the "doesn't exist" conclusion above deserved a second look
  before being trusted, and it was wrong -- not about the build, about
  this file's own reading of it:

  `MonoImage.class_cache` is a `MonoInternalHashTable`
  (`mono/utils/mono-internal-hash.h`, confirmed against real Mono
  source): it does not allocate its own chain nodes for collisions --
  each bucket slot holds only the *first* class that hashed there, and
  every subsequent collision chains through a pointer embedded in the
  class itself. `struct _MonoClassDef`
  (`mono/metadata/class-private-definition.h`) names that field
  `next_class_cache`, "next element in the class_cache hash list (in
  MonoImage)". `dump_class_names` (main.rs) read one `MonoClass*`
  straight out of each bucket slot and stopped there -- silently
  dropping every class chained behind the first one in a bucket that
  already held something else. `GameState` was one of them.

  Fixed: `dump_class_names` now follows `next_class_cache` for every
  bucket (new constant `mono_layout::MONO_CLASS_NEXT_CLASS_CACHE =
  0x108`, confirmed live -- walking every bucket's chain at this
  offset raised total distinct classes found from 20795 (flat) to
  29171 (+8376, +40%) against the real running match, average chain
  length 1.22 [consistent with a healthy hash-table load factor, not
  the wildly-varying depth an unrelated-but-plausible field like
  inheritance-chain `parent` would produce], and `GameState` was only
  reachable this way; independently cross-checked by hand-computing
  forward from `class-private-definition.h`'s field list, landing
  within one plausible struct-padding choice of the same offset).
  `GameState` (and `GameMgr`) now resolve reliably via
  `find_singletons` -- `MonoClass*`/`MonoVTable*` both found, stable
  across repeated runs.

  **Not yet closed**: `GameState.s_instance` itself still doesn't turn
  up via `find_self_typed_static`'s scan window
  (`vtable+0x48..+0x3000`), and widening that to `+0x8000` by hand
  found nothing either. Given the *class* lookup was the actual bug
  (not a wrong assumption about where instance-of-self statics live --
  that worked fine for `Player`'s one real hit, found the same way,
  earlier this session), the likely next explanation is that
  `MonoVTable`'s static data for a class with GC-tracked static
  fields (`GameState.s_instance` is a reference type, so GC-tracked)
  is NOT stored inline after the vtable's method table at all, but in
  a separately-allocated block reached through a different `MonoVTable`
  field this file hasn't located -- a different, narrower unknown than
  "which class" now that this one is resolved correctly.

  Also: every earlier session artifact built on the un-fixed
  `dump_class_names` (`--find-all-singletons`'s PowerSpellController
  lead, `--find-refs-to`'s all-zero result) was run against the
  *undercounting* class list and should be treated as provisional --
  re-running them now that chaining is fixed may turn up what they
  missed, PowerSpellController's own indirect reference chain
  included.

  **`s_instance` FOUND, 2026-09-02, same session.** The reason it
  didn't turn up in `find_self_typed_static`'s scan window: per real
  Mono source (`mono/metadata/class-internals.h`, `struct MonoVTable`),
  `has_static_fields`'s doc comment says the vtable-array's trailing
  slot (`vtable[vtable_size]` -- exactly this file's own "computed"
  offset, already printed but never read as data) holds a *pointer to*
  the real static-data block, not the block itself inline. Reading
  that one pointer and scanning *its* target (not the vtable's own
  neighbourhood) found `s_instance` immediately, at offset +0x0 of the
  block, on the first try, against a real live match:

    GameState.s_instance @ 0x13174fa80 (own klass confirmed = GameState)
      +0x40  -> 0x75d91000, klass StandardGameEntity  ("m_gameEntity")
      +0x28  -> Map`2 whose values array is klass Entity[]   ("m_entityMap", ~94 live entries)
      +0x30  -> Map`2 whose values array is klass Player[]   ("m_playerMap")
      +0x38  -> Map`2 whose values array is klass SharedPlayerInfo[]
      +0x70  -> Map`2 whose values array is klass EntityChoices[]
      +0x160 -> Map`2 whose values array is klass TurnTimerUpdate[]
      +0x138 -> PowerProcessor instance (the same class this file
                already tries as a `find_singletons` target, itself
                with no self-typed static of its own -- reached
                through GameState instead)

  `m_playerMap`'s values array, read directly (`MonoArray.max_length`
  at +0x18, elements starting at +0x20 -- Mono's ordinary array
  layout, `try_mono_string` already assumes the analogous string
  layout elsewhere in this file): **exactly two live `Player`
  objects, definitively, no heuristic involved** --
  `Player[0]` name="xror" playerId=1, `Player[1]` name="Sudowoodo"
  playerId=2 (both read via the already-confirmed `PLAYER_NAME`/
  `PLAYER_PLAYER_ID` offsets). This closes A.7 for real: no more
  heap-wide scanning, no more topology scoring, no more risk of a
  stale finished match's Player object being picked -- `GameState`'s
  own `m_playerMap` *is* the current match's authoritative roster,
  the same way HearthMirror's public sources (S6, S7) describe.

  `Map`2` is a custom hash map (an `Int32[]` bucket-index array plus a
  `Link[]` open-addressing chain array plus parallel key/value arrays
  -- NOT `System.Collections.Generic.Dictionary`), so its own internal
  layout (which field is "keys" vs "values", bucket/link semantics)
  is not needed at all for this -- only the *values* array pointer
  (a fixed field offset within the `Map`2` object, empirically +0x28
  across all five instances found) and Mono's ordinary array layout,
  both far simpler than reverse-engineering a real hash table's
  internals would have been.

  Field offsets used above (GameState-instance-relative, and the one
  `Map`2`-relative) are confirmed against one live process this
  session only -- same evidence bar as everything else in this file,
  not yet cross-checked against a second, independent match/session.
  Next step: wire this into `memreader` properly (a new confirmed

================================================================
A. MEMREADER: SIDES SOMETIMES SWAP PLAYERS
================================================================

A.1 Symptom
-----------
`--snapshot` / `/api/memory` `sides` can attach the wrong Player
objects. Hands, heroes, and battleTags swap. Documented live
2026-09-01 in tavernlab-sim/memreader/README.md.

Flat `entities` and `players` lists are more honest: they do not
claim "whose". `sides` is a derived view that *does* claim that.

A.2 Current pipeline
--------------------
1. Scan anonymous rw maps (`/proc/PID/maps`, empty pathname) for the
   literal MonoVTable* of class Entity (cap 12_000) and Player (cap
   200). Chunk 4 MiB, scan-byte cap 3 GB. First hits in map order
   win; later regions are never visited once the cap is hit.

2. game_entity(): among Entity hits with id == 1, prefer those that
   still carry TURN (tag 20) or STEP (tag 19). If that pool is empty,
   take every id==1 and pick the one with the most nearby id 2/3
   within 0x10_0000.

3. current_game_entities(): keep hits whose address is within
   SAME_GAME_WINDOW = 32 MiB of that GameEntity, then cap by max id
   in the window (plus HERO_ENTITY+2).

4. build_sides(): for playerId 1 and 2, take Entity id 2/3 from the
   live set, then pick a named Player with matching player_id inside
   the same 32 MiB window. If none is in the window, fall back to
   the nearest named Player of that player_id *anywhere*.

5. CONTROLLER / ZONE slice cards onto sides *after* the island is
   chosen. They do not choose the island.

6. collect_player_hits() reads Player.entity_id from ENTITY_ID
   (+0x38), the offset confirmed on *Entity*, not on Player (name is
   at +0x120). Live dump: real pair had entity_id ~1e9, stale pair
   had a negative garbage word. Neither is a join key.

A.3 Why this cannot become reliable by tuning the window
--------------------------------------------------------
Boehm (mono-2.0-bdwgc) does not move objects. Finished matches stay
on the heap until collected. A vtable scan always sees several
complete games with the same EntityIDs (Game=1, Players=2 and 3).

Proximity is allocation-era, not identity. 32 MiB is an arbitrary
cut. "More nearby 2/3" prefers a *finished* fuller board over a
mulligan-fresh live game -- already observed.

TURN/STEP on id==1 is not guaranteed in the scanned tag lists. The
2026-09-01 dump: *neither* id==1 candidate had those tags, including
the island that actually held the live Players. game_entity() then
did not land in that island.

The 32 MiB filter is correct *if the anchor is right*. Offline test
build_sides_prefers_a_player_in_the_same_heap_island_over_a_closer_stale_one
proves only that. The live failure is the anchor, plus the
nearest-overall fallback when the window misses.

Scan order + max_hits can omit the live GameEntity entirely
(README suspicion: "maybe the real live GameEntity never entered
the id==1 candidate list").

A.4 How HDT / HearthMirror actually do this
-------------------------------------------
They do not cluster leftover heap instances.

Path (public HearthMirror snapshot / UnitySpy / HDT Watchers):

  mono_get_root_domain
    -> MonoDomain.domain_assemblies until image name Assembly-CSharp
    -> MonoClass statics (typically s_instance)
       UnitySpy: _MonoClass->runtime_info->domain_vtables->vtable
       + VTableSize, then the field
    -> GameState.s_instance.m_playerMap (keySlots / valueSlots),
       skip slots whose class is not Player
    -> GameMgr.s_instance for match metadata (m_gameType, spectator,
       missionId)

Current-match Players come from that map, not from a global Player
vtable scan. Power.log reconstruction is a *separate* watcher.
Official HearthMirror is not in the HDT tree (shipped zip + hashes).

No inspected HearthMirror/HDT source roots GameEntity via
Network.GetGameState; that name is the network protocol, not the
mirror walk. Closed-source field names after ~2017 (entity cache vs
m_playerMap / m_entityMap) were not inspectable; only
GameState.s_instance.m_playerMap is evidenced in the public snapshot.

A.5 Wine / process_vm_readv (constraints that stay)
---------------------------------------------------
Under Wine on Linux, Hearthstone.exe is already a native x86-64
Linux process. process_vm_readv needs no Windows debug layer.

Access: same UID (not root/sudo) or CAP_SYS_PTRACE; Yama
ptrace_scope 0 or 1. Scope 2/3 blocks the read.

Remote::read treats any short copy as failure. The heap scan still
advances by the requested len, so a short iovec skips that chunk.
plausible_ptr keeps non-null pointers in the canonical low half
(< 0x0000800000000000).

Legal posture (docs/DESIGN.md): read-only, user's own process, never
merged into tracker.rs, never silent fallback between log and
memory, no traffic intercept, no input emulation.

A.6 Better methods for sides (ranked)
-------------------------------------
1. Singleton walk (same class of trick as HearthMirror; best).
   Resolve GameState / EntityMgr / GameMgr statics from
   Assembly-CSharp. The class walk already exists:
   find_singletons() / find_self_typed_static() (main.rs ~1396)
   already target GameState via --deep. No static-field offset is
   confirmed live yet (Entity / Player are; GameState is not).
   That function already notes the singleton may be a ServiceLocator
   rather than a self-typed static -- so "infrastructure exists" is
   not "the offset is almost in hand". If --deep still finds no
   s_instance, the next step is the locator, not a wider heap window.
   Follow only objects reachable from the confirmed root. Stale heap
   copies are never candidates. Still process_vm_readv only. Same
   evidence bar as mono_layout.rs.

2. Until that offset exists: score *islands as whole games*.
   Union-find on address (gap from measured dumps, not 32 MiB).
   Score topology from the game-state protocol:
     one Game id=1, two Players id=2,3,
     CONTROLLER in {1,2},
     <=7 minions PLAY, <=10 HAND, heroes in PLAY,
     dense id range 1..cap,
     STEP in a live range (not GAMEOVER),
     named Player pair with PLAYER_ID 1 and 2.
   Pick argmax. Do not fall back to nearest-overall Player.
   If the winning island has no named Player, name=null and
   confidence=low.

   Boehm is non-moving: a temporal prior (prefer the island that
   overlaps the previous snapshot's addresses) is cheap and strong.

3. Join Player to a side without +0x38.
   Use List<Tag> on the Player object: PLAYER_ID (30), ENTITY_ID (53),
   HERO_ENTITY (27), RESOURCES. Match to Entity id 2/3 in the winning
   island. Drop the struct field until an offset is confirmed live
   the same way PLAYER_NAME was.

4. Scan completeness: do not stop at 12_000 if no legal island has
   been seen; finish remaining rw regions. Prefer walking
   EntityMgr's dictionary once the static is known.

5. Honest uncertainty: if topology score is low, omit sides names /
   skip sides rather than swap. Optional diagnostic compare to the
   log tracker without merging (DESIGN rule 4).

Do not: enlarge SAME_GAME_WINDOW; rank only by neighbor count; trust
Player+0x38; merge log + memory on disagreement.

A.7 Implementation plan (memreader)
-----------------------------------
PR 1 -- stop the harmful fallback
  Remove nearest-Player-overall when the window is empty.
  Stop treating Player+0x38 as entity_id; use tag 53.
  Add confidence or skip sides when topology fails.
  Tests: existing stale-nearer-than-live; no in-window Player must
  not invent a name from another match.

PR 2 -- island scoring instead of game_entity + 32 MiB
  Union-find; score; current_game_entities = that island's dense
  1..cap. Synthetic tests from the live dump shapes already in
  main.rs tests (stale fuller board vs live mulligan; two id==1
  with no TURN/STEP; correct pair with garbage field ids).
  Keep SAME_GAME_WINDOW as a debug metric, not the join.

PR 3 -- find the singleton (the actual fix)
  --deep already looks for a GameState self-typed static. Dump that
  hit (or the empty "ServiceLocator, not a static field" path) plus
  GameMgr / EntityMgr / InputManager. Confirm one root against
  Power.log in the same session (same evidence style as HERO_09dbp /
  id=57). Snapshot follows that root; heap scan becomes a fallback
  diagnostic. Do not treat a miss as a reason to enlarge
  SAME_GAME_WINDOW.

PR 4 -- temporal lock + scan completeness
  Remember last-good island addresses across /api/memory polls
  (server-side). Finish heap regions if no legal island yet.

depth=10 / budget=50_000 (watch/mod.rs, comment at the Planner::new
call), a turn with 6-7 attackers plus a spell, hero power, and The
Coin is already 10+ actions.

search() at depth==0 calls eval(). eval() returns Outcome::Win
(1.0e6) only if Game::is_over() is already true. Remaining legal
attacks are invisible. The search prefers a locally better trade.

Independently: if budget hits 0 mid-level, search returns None and
level() discards the *entire* level, even if a sibling already
scored Win. Iterative deepening then keeps the last *complete*
shallower level, which may never have explored the lethal line at
all.

plan() re-chooses up to 16 times, one action at a time. That does
not save a lethal whose *first* action was not selected, because
the wrong first trade already spent the attacker.

B.3 Why "just raise depth" is the wrong fix
-------------------------------------------
Branching on a wide board is large (attacks * targets * plays).
Budget dies *inside* a deep level; iterative deepening then
silently keeps a shallow complete result. The failure mode is
identical to depth=4, only on a wider board.

Lethal and "play well" are different questions. Mate search is not
positional eval. Uniform DFS with a heuristic at the leaf will
always have a horizon.

B.4 Better methods for lethal (ranked)
--------------------------------------
1. Compress the attack phase in eval (largest gain per line).
   While it is still our turn and the game is not over, a leaf may
   count *already legal* face damage without spending depth.

   Bound (lower bound only; never a guess through a blocker):

     enemy Taunt in PLAY          => do NOT declare Win
     opponent secret in zone      => do NOT declare Win from static
                                     (live advice; engine does not
                                     model Ice Block / Noble Sacrifice
                                     on the hero, so a static 1e6 would
                                     be a kill the real client can still
                                     eat. Leave those lines to search.)
     else:
       minions: for each with can_attack_face(), add
                atk * (max_attacks() - attacks_done)
                -- can_attack_face() is a boolean (Rush vs Charge,
                summoning sickness, remaining swings > 0). It does
                *not* count Windfury's second hit. Using it as the
                sum's only filter undercounts a 4/4 Windfury.
       hero:    add weapon atk if the hero can still swing
       hero power / 0-cost damage only if mana is already there

   If that lower bound >= enemy hp+armor, score 1.0e6 (same as
   Outcome::Win). Seven 1/1s into face stop costing seven plies.
   depth=10 remains for spells, Coin, hero power, and punching Taunt.
   This is quiescence / static lethal, not "search deeper".

   Immune: Keywords::IMMUNE is checked on minions in deal_damage;
   damage_hero() does not. Hero Immune / Ice Block is absent
   mechanics, not a missed branch in eval -- except the secret
   rule above, which is for live advice vs the real client.

2. Dedicated lethal probe before the heuristic plan (live only).
   Tree of damage-relevant actions only: attacks, damage spells,
   hero power, weapon, Coin if it unlocks damage. No "play a 3/4".
   Iterative deepening, face/damage ordered first, stop at hp<=0.
   Disproof: upper bound on available damage (taunts/shields
   counted) < hp.
   If a line exists, that line *is* the plan. eval() does not vote.
   If not, run the current planner (depth 4-6 is enough for trades).

3. Do not throw away Win when budget dies (a bug, not a heuristic).
   When best >= WIN, return Some(best) immediately.
   When budget==0: if best >= WIN then Some(best), else None
   (do not mix a partial heuristic level with a complete one).
   Iterative deepening stays honest for eval scores and stops
   hiding a proven mate.

4. Do not:
   blindly set depth=16 / budget=200_000
   treat "almost lethal" as Win through Taunt / Divine Shield /
     an opponent secret
   change greedy agent.rs / policy knobs without re-measuring
   replace the 50_000/10 live stopgap -- it stays for Taunt lines

B.5 Implementation plan (planner / live advice)
-----------------------------------------------
A. Fail-soft / early-exit on 1e6 in search/level.
   When best >= WIN, return Some(best) immediately.
   When budget==0: if best >= WIN then Some(best), else None
   (do not keep a partial *heuristic* level).
   Test: found Win, then budget=1 on remaining siblings => first
   action still from the lethal line.

B. Static lethal in eval (face, no Taunt, no enemy secret).
